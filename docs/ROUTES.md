## Rebuilt in v4

| Path | Notes |
|---|---|
| `/` | public landing, written for the SME first: hero (*Map, match, make*), then **For your business** — five coloured bands, one per thing the product does (Map → the directory, Market → the marketplace, Participate → events, Measure → the Compass, Improve → the Learning Hub), then the other audiences (facilitators and urban administrators → an email for a demo, researchers → `/register`, which already accepts an account without an organisation), then the pilot notice and about. Content follows the project's landing doc, minus three things it asked for that are not true or not built yet: job and funding listings (the product has neither), the success-stories slider fed from the Learning Hub (a feature, not copy), and a privacy section the doc left unwritten — inventing data-protection claims is not a copy decision. Signed in → the org dashboard, or `/home` without an org. Pending actions and the activity feed of the old `/` go to the dashboard. An expired session on a public page (landing, marketplace, public profile) just means "visitor"; on a signed-in page it goes to `/login` (`lib/session.ts`) |
| `/home` | signed in without an organisation: "Add your organisation" |
| `/$orgSlug/assessments`, `…/$formKey` | Compass. The list asks `GET /forms?organization_id=`, which already carries this organisation's answers: status (not started / in progress / completed), score ring, and how many are done. The questionnaire renders the six field types (text, email, select, multiselect, rating, table), hides questions whose `condition` is not met, and saves on its own — `POST /answers` the first time, then `PATCH` (the API deep-merges). Status and score are the server's to decide |
| `/global` | Directory: every organisation, filtered by search, **what they are** (the 12 kinds, in the shared checkbox menu — twelve permanent pills was a wall, and a kind says what an organisation *is*), **what they do** (the five value-chain activities as pills, each carrying its own tone — the same hue the marketplace gives that part of the chain), where (near my organisation + radius, country) and status (on FABRIX / claimable). An activity is a heading and never a stored value: organisations keep categories and subcategories in `specialties`, so a picked activity travels to the API as the categories underneath it (`categoriesForTypes`), which `with_specialties`' plain array overlap then matches. Cards, list or map — the map colours claimable ones amber, and its payload (`view=map`) has no `claimed`, so the list's knowledge is passed to it. Each row opens the public profile |
| `/events`, `/events/$eventId` | auth. List: search, upcoming / past, near my org + radius, country; cards / list / map. Detail: when and where (or the link, for an online one), description, RSVP (going / maybe / can't go — answering again changes it, clicking the same answer takes it back), who is going, and edit / delete for its creator. Adding and editing happen in a dialog, on the shared `EventForm` (the online switch swaps the address for a URL) |
| `/$orgSlug/relations` | Connections: the partners you work with, from the profile payload (`relations` + `related_organizations`). Add one (search → relation type → optional note, `POST /relations`), remove one, see which are not claimed yet. An organisation not on FABRIX is added through `/organizations/new`, which invites it |
| `/$orgSlug/settings/members` | **gone** — redirects to `/$orgSlug/profile?tab=team`. The team, its invitations and the join requests live in the profile's Team tab (the PM's prototype). The tab also holds the way **out**: the last remaining member can give the profile back (`POST /organizations/:id/unclaim`), which returns it to the directory as an unclaimed entry rather than deleting it. That distinction is the whole point — every association of an organisation cascades on destroy, and three of them belong to other people: the relations other organisations declared toward it, the records facilitators keep about it, and everyone's bookmarks. What leaves is what the team put in (memberships, the private figures, the Compass answers, the listings, and invitations or join requests to a team that is dissolving). Offered only to the last member, because with colleagues still there it would evict them too — the API refuses that, so the button would be a dead end |
| `/$orgSlug/dashboard` | signed-in home, from the design system's Home screen: greeting, pending actions (join requests on orgs you own → the profile's Team tab, invitations received, your claims and join requests), "The loop" (add a partner → `/organizations/new`), your network (connections + profile essentials → editor), "Around you" (`/feed?organization_id=`, show more). Not rebuilt: the design's network-wide "partners invited this month" counter and "Yours: X invited, Y joined" — no API for them |
| `/messages`, `/$orgSlug/messages` | messaging — one page for both mailboxes: with an organisation slug it keeps the conversations that organisation is a side of and answers in its name, without one it shows everything you are part of and answers as you (`GET /conversations` returns both; there is no per-organisation endpoint). Mailbox on the left (who, last message, unread count), thread on the right, the open one in `?conversation=`; on a phone one replaces the other. Enter sends, Shift+Enter breaks the line. Opening a thread marks it read (`PATCH /conversations/:id/read`) and refreshes the sidebar counter. Conversations are *started* from a profile or a listing (`ContactOrganizationDialog`), never from here — and always **in the name of one of your organisations**: messaging was the one place where a person was a correspondent, which gave everyone two mailboxes and let the one you happened to write from fix your identity in that thread forever. The person is never hidden (every message carries its author, signed "Name · Organisation"); what changes is that the thread belongs to the organisation, so colleagues see it and it outlives whoever opened it. A single-organisation sender is told rather than asked to pick from a list of one; someone with no organisation gets the reason and a link to create one, not a button that quietly fails. Only *creation* is org-only: threads opened under the old rule keep their human side, stay listed and can still be answered — which is why the personal mailbox is still here, and stays until the data migration converts them. The API enforces the same rule in `ConversationsController` (not as a model validation, or legacy rows could be neither updated nor migrated), with one exception: an admin may still write to a person, because the support channel answers whoever sent a feedback |
| `/notifications` | the server writes each message (`NotificationMessageBuilder`), so the page renders it as is rather than composing text per type. All / Unread in `?filter=` — the index takes no unread filter, so Unread narrows what is already loaded. Opening one marks it read, "Mark all as read" clears the lot, both refresh the sidebar counter. Paging is by feel: `GET /notifications` is paginated by Pagy but answers `{ notifications }` with **no meta**, so a full page is the only sign another may follow. Community and challenge types are legacy — those rows render without a link; the rest lead to the profile's Team tab, an organisation, or an event |
| `/settings` | Account and Notifications in `?tab=`. **Account**: photo (direct-to-S3 on the `User` record), name, email and password as four separate blocks, because the API's rules differ — `PATCH /me` demands `current_password` to change an email or a password, and a new email reverts the account to unverified and sends a fresh verification mail. Then deleting the account (`DELETE /me`) behind a dialog, which signs you out and clears the cache. **Notifications**: `GET /notification_preferences` lists every type — retired ones are hidden rather than shown under a raw key — with On / In app / Email; the three action-required types come back `mandatory` and their switches are disabled, since the API refuses to change them (422). The two channels are disabled while a notification is off |
| `/facilitator`, `/facilitator/$networkSlug` | **one dashboard per network**, and the sidebar lists them all — `me.networks` already carries them, so there is nothing to fetch and nothing to switch between once you are inside one (this replaces the old front's `?network=` + localStorage selection, and its "My network" page). `/facilitator` opens the first, or explains how to get one. The features are tabs, like the profile (`TabLink`, `?tab=`): **Overview** (organisations followed, open tasks, overdue, what is next, the territory), **Organisations** (the CRM records as a **table** by default — a working list before it is a gallery — or cards, or a map, or the network **graph**, in `?org_view=`; filtered by search, kind, speciality, economic health, country and declared workforce, each in the URL so a filtered list is shareable. Kind and speciality are multi-value, so they are Radix checkbox menus rather than pills: thirty-five permanent pills made the panel unreadable, and the menu keeps itself open across ticks — only the chosen values stay on the page, as removable chips. Speciality is the **listing taxonomy**, the way the profile editor offers it: grouped under the five activities, a checkbox per category, and a picked category opening its own subcategories. An activity is a heading and never a value — organisations store categories and subcategories in `specialties`, never the type, and the API's filter is a plain array overlap that does not expand a category into its children), **Tasks** (add, tick, delete; to do / done in `?tasks=`), **Team** (who has access, colleagues to grant it to, pending invitations, invite by email), **Settings** (everything `PATCH /networks/:slug` accepts: name, description, the organisation that runs the network, and the territory — centre picked from Photon plus a radius. The map draws that territory as a light blue translucent disc (`fx-sky`, `PointsMap`'s `areaColor`/`areaOpacity`, which the explore pages leave at their own default), centred on the point set here — or, when none is set, on the organisation that runs the network, whose coordinates travel on the session payload since the network's own `organization` field carries none. The legend names whichever centre is in use. The slug is deliberately left out: changing it would break every link already shared). The API refuses to remove the network's creator (403) and the last member (422), so neither is offered — the creator's row reads "Creator" instead. The map and the graph both ship. The graph is loaded lazily (`react-force-graph-2d`), so its force layout and canvas renderer stay out of the main bundle; nodes are coloured by the economic health the facilitator set and sized by the declared workforce, dashed links are the matchmaking suggestions rather than declared relations, and it draws the **whole** network — the API's graph endpoint takes no filters, which the view says out loud rather than letting the filter panel above imply otherwise. **The space is tinted apart** from the rest of the platform — it is a work surface, not the organisation-and-people side: the layout route stamps `data-space="facilitator"` on `<html>` and `index.css` swaps four variables under it (`fx-panel`, `fx-emphasis`, `fx-emphasis-soft`, `fx-line`) to indigo on a cooler grey. No component changes, because components read token *names*. It sits on `<html>` and not on a wrapper so that dialogs — which Radix portals to `<body>` — are tinted too; the route removes the attribute on the way out |
| `/facilitator/$networkSlug/organizations/$recordId` | **the CRM sheet — not the public profile**, which is what a facilitator opens from the Organisations tab. It holds what this network knows and the public profile never shows: the health the facilitator sets (economic and environmental, edited in place), their notes (saved on their own, one PATCH per pause), the needs they assessed with a note each (`needs` jsonb — the keys match production data, do not rename them), the figures this network keeps (turnover, employees, growth), the organisation's people with their emails, **the tasks attached to this organisation** (the network's own tasks, narrowed through `?network_organization_id=`, added from here already linked — the row component is shared with the Tasks tab), the logged interactions (call / email / meeting / visit), and the organisation's **own** needs form read-only — that one is the organisation's answer, reusing the Compass queries and its `isVisible` (extracted to `features/compass/visibility.ts` so both share it). The public profile is one click away in the header. Unfollowing deletes the whole record, so it asks first |
| `/manual`, `/manual/$page` | the **user manual**, in the platform's own design — open to visitors (`_open`: the app's sidebar once signed in, the public frame otherwise), because it is worth reading before signing up. Real paths rather than a search param, so every page is linkable; `/manual` opens on the first page instead of a table of contents the side nav already shows. `features/manual/contents.ts` is the table of contents and lists **only pages that are actually written** — a chapter opening on nothing is worse than one not announced. Sections so far: *Start here* (Getting started) and *Your organisation* (Your profile, What you do). **What you do renders the taxonomy from the very modules the app imports** (`listings/taxonomy`, `organizations/kinds`) — never from a copy, so the manual cannot describe a vocabulary the product no longer offers, the way `/design` cannot drift from the tokens. Reached from the sidebar's Resources group and from the public footer. Not the Learning Hub: that site is Directus content edited by the project partners, this documents the product |
| `/login`, `/verify-*`, `/forgot-password`, `/reset-password` | |
| `/register` | one wizard: find your organisation → claim it / create it (details, address on the map, specialties) / "I'm not part of one" → account. Replaces the old hub, `/register-basic` and `/register-with-org` |
| `/organizations/new` | search → claim an unclaimed one, or create: **mine** (`owner_email: ""`, I own it) or **a partner** (`owner_email` = their email → they are invited to claim it) |
| `/data` | **where the industry actually is**, from the public business registers the project mapped: Rotterdam (LISA, six snapshots from 1997 to 2022) and Athens (GEMI, with an option to match a business on its secondary activity codes). One page, the city in `?city=`, everything else in the URL too (`cats`, `year`, `hexbin`, `secondary`) so a filtered view is a link — none of those names is used by another route, since search params are shared router-wide and `tab`, `type` and `view` are all taken. The old front carried one ~600-line page per city, near-identical twins; here the city is data (`cities.ts`) and the page is one component. The map draws one source and layer set per selected activity, coloured by the NACE category's own `color_hex`, either as every address (clustered while zoomed out) or aggregated into ~500 m hexagonal cells sized by count — `PointsMap` could not serve this: it places one marker per point and caps at 160. Kept **signed-in only**: these registers name individual businesses with their address, and `DataImports::BaseController` has always required a session. The category list is fetched by the route loader and held for an hour — a public register does not move while you browse. Popup contents are escaped, which the old front did not do |
| `/admin`, `/admin/organizations` | **system admins only**, guarded in `beforeLoad` and refused again by every `/admin` endpoint. Lists are worked through rather than browsed, so they page (`Pagination`) instead of scrolling infinitely, and they **sort in the query**: nothing in the codebase sorted server-side before, so `Organization::SORTABLE` establishes the pattern — an allowlist, because the column name arrives from the URL, plus `id` as a second key so rows sharing a value cannot shuffle between pages and appear twice or never. Sorting the loaded page instead would answer "first by name" with the first of thirty rows, true of nothing. One schema for every admin list (`features/admin/search.ts`): they all search, sort and page alike, and search param names are shared router-wide anyway — `q`, `kinds`, `status` and `country` already existed with these exact types, only `sort_by`, `sort_direction` and `page` are new. The table shows only what the payload carries: the admin index renders `OrganizationBlueprint`'s **default** view, where workers and turnover are absent (they live in `:extended`), and widening that view is not an option — the public endpoint serves it too. Networks, claims and feedbacks come next; a tab leading nowhere is worse than one not announced |
| `/design` | the v4 catalog |
| shell (sidebar, org switcher, user menu, unread counts) | every entry leads somewhere real — the temporary `PagePlaceholder` is gone, and so is its component |
| `/marketplace`, `/marketplace/$id` | open to visitors; filters: search, then **the shape of the exchange** on its own ground — offered or wanted (`direction`), and one-off or ongoing (`one_off`, filterable both ways round, so the standing arrangements can be isolated too). Both were in the product's language long before its data: the page lede promised "offered and wanted" and the catalogue reserved the solid orange badge for it, while the column did not exist. They lead every badge row — card, list and sheet — because which way a listing runs decides whether it is any use to you before what kind of thing it is. Then **activity** → category → speciality (the activity pills carry each type's tone, so the colour means the same thing here, on the cards and in the directory). "Activity" is the word users read for the top level of the taxonomy; the API's own names (`listing_type`, `by_type`) are left alone, so the rename is a label change and not a contract change. Near my org + radius, country; cards / list / **map** (MapLibre + Carto Positron, keyless: clustered pins coloured by listing type, the radius filter drawn as a circle, a card on click; `?view=map` fetches them all through `GET /listings?view=map`) |
| `/marketplace/new`, `/marketplace/$id/edit` | photos upload after create / immediately on edit |
| `/$orgSlug/listings` | **gone** — redirects to `/$orgSlug/profile?tab=edit&section=offers-needs`. Offers are listed there, and created or edited in a dialog (`NewListingDialog` / `EditListingDialog` wrap the same `ListingForm` as `/marketplace/new` and `/marketplace/$id/edit`, which the marketplace keeps) |
| `/organizations/$id` | public profile (slug or UUID), open to visitors: header, about, listings, photos, connections, contact / specialties / networks. Actions by viewer: member → edit + add a listing; visitor → sign in; other member → connect (relation), message (claimed), request to join (claimed) or claim (unclaimed). Private data (workers, turnover, NACE…) is **not displayed** — but the API still returns it publicly |

**Marketplace — left for later:** map view and "near a city" search (with events/directory, same explore
frame); closed or expired listings of your own org are not listed (the API index returns available ones only);
"Posted by" does not link to the org yet (public profile not rebuilt).

## Shared building blocks to rebuild

- **Explore framework** — `explore/ExploreShell`, `ExploreFilters`, `InfiniteScrollSentinel`, `lib/explore.ts` (location defaults to "Me", 100 km)
- **Maps** — MapLibre `PointsMap` (generic) ; hexbin maps only for data pilots
- **Address autocomplete** — Photon (`PhotonAddressAutocomplete`, `lib/geocoding.ts`)
- **Uploads** — presigned `/uploads/presigned_url` + direct PUT ; listing images, org photos, avatar
- **Messaging** — `MessagingLayout`, `MessageBell`, `lib/conversations.ts`
- **Notifications** — `NotificationBell`, `lib/notifications.ts` (`getNotificationUrl`)
- **Taxonomies** — listing types/categories, `ORG_KINDS`, specialties, NACE codes, facility types, countries
- **Org wizard** — search → claim or create (register + `/organizations/new`)
- **Referral** — invitations, join requests, relations, pending actions
- **Activity feed**, **dynamic forms** (`lib/forms.ts` conditional questions + `lib/answers.ts`), **charts** (recharts), **network graph** (react-force-graph-2d)
